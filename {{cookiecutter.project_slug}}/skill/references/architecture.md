# 架构与设计准则

## 先建模，再编码

业务变更开始前，先用简短设计说明回答：业务不变量是什么、状态如何迁移、谁有权操作、
事务边界在哪里、重试是否安全、哪些外部副作用应在提交后执行。对现有功能优先扩展已有边界，
不得为完成局部需求再建一套平行模型、服务或状态。

## 分层与依赖方向

- `views.py` 和 Admin 是交付层：处理 HTTP/Admin 输入输出、身份与消息，不编排长业务流程。
- `forms.py` 验证输入形状和单对象规则，不执行跨模型写入。
- 应用服务编排用例、事务和权限不变量；模型保持自身数据不变量与简短领域行为。
- QuerySet/selector 封装反复的读模型和 `select_related`/`prefetch_related`，不承担写用例。
- Celery task 只是调度与重试边界；Provider 或 Gateway 隔离第三方协议。

业务 App 不得从另一个 App 的 `views.py`、`forms.py`、`admin.py` 或信号处理器导入能力。
跨 App 调用必须通过对方公开的 service/selector 入口；若一个用例同时编排三个及以上业务域，
将其定位为显式应用层服务，并在测试中固定依赖边界。禁止用 signal 隐式编排核心交易流程。

## 服务与文件的演进

`services.py` 只适合规模较小的业务域。出现以下任一情况时，必须在本次设计中评估拆分，
若暂不拆分则在迭代记录中说明原因：

- 单文件超过约 400 行，或同时包含三类以上用例。
- 单函数超过约 50 行、分支过多，或同时完成校验、查询、状态迁移、通知。
- 循环中包含多次 ORM 读写，或一个服务直接依赖三个及以上业务 App。

拆分时优先按用例命名，例如 `services/checkout.py`、`services/payment.py`、
`services/fulfillment.py`，并通过 `services/__init__.py` 保持稳定的公共导入。不为追求文件数量而制造
只转发调用的空抽象。

## 状态、事务与副作用

- 状态迁移由单一服务入口管理，显式校验起始状态、操作者、终止状态和重复请求。
- 金额、库存、信用、订单、退款等竞争写入使用 `transaction.atomic()` 和必要的
  `select_for_update()`，数据库约束作为最后防线。
- 在交易内发送通知、邮件、Celery 任务或调用外部 API 时，默认使用
  `transaction.on_commit()`；外部回调和任务必须有可验证的幂等键。
- 不得吞掉异常。可预期的业务拒绝使用具体业务异常；只在系统边界捕获宽泛异常，记录上下文并决定重试或失败。

## 读模型与性能

列表页必须分页，并对模板会访问的关联显式使用 `select_related` 或 `prefetch_related`。
为高频页面或 Admin 仪表盘增加查询时，使用 `django_assert_num_queries` 或等价方式固定查询上限。
不在 context processor 中执行无缓存的重聚合或多次查询。

## 设计验收清单

1. 公共入口、依赖方向和业务不变量清晰。
1. 权限、幂等、并发和事务失败路径有自动化测试。
1. 新增代码没有让已超阈值的文件或函数继续恶化。
1. 重要查询的数量和索引与真实访问路径一致。
1. 文档、生成 Skill、代码、migration、SQL 和测试没有相互矛盾。
